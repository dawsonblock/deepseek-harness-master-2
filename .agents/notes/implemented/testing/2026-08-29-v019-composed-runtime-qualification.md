# Agent Note: v019 composed runtime qualification gate

Status: implemented

English | [中文](2026-08-29-v019-composed-runtime-qualification.zh.md)

> Isolated mechanisms can pass while dependency injection, configuration resolution, plugin ordering, or registration causes the paid-evaluation graph to use the wrong implementation.

## Problem

The existing security qualification (`v019-security-qualification-v2`) inspects source strings and calls individual APIs with synthetic sessions. It cannot detect defects caused by dependency injection, configuration resolution, plugin ordering, or service registration — the same class of defect previously seen with `fs-local`/`fs-sandbox` composition, where isolated mechanisms pass while the paid-evaluation graph uses the wrong implementation. A stronger gate was needed that boots the exact configuration generated by `generateRepoConfig()`, resolves the actual running services from the Cordis context, inspects the effective graph, exercises real model-facing capability paths, and persists an artifact bound to the exact source and configuration inputs.

## Decision

Added `v019-composed-runtime-qualification-v1` (`scripts/v019-composed-runtime-qualification.ts`). The qualification script reuses `generateRepoConfig()` to produce the exact Batch A `.v019-cordis.yml`, boots it through the real Loader, mounts the production `RepairRuntime` plugin, and runs 15 checks:

- **C1**: Effective composition identity — queries `ctx.get()` for `fs`, `shell`, `sandboxPolicy`, `goals`, and `repairController`, asserting constructor names and policy mode.
- **C2**: File-tool isolation — exercises the registered filesystem through workspace read/write (pass), outside read/write (deny), and parent traversal (deny).
- **C3**: Bash isolation — exercises the registered shell through workspace read (pass), external path read (deny), DNS lookup (deny), HTTP connection (deny), and git fetch (deny).
- **C4**: Model workspace contains no Git history.
- **C5**: Holdout secrecy — agent cannot find or read holdout files; verifier can read them.
- **C6**: One-shot lifecycle — `handleVerificationPass` with a passing holdout verifier produces `verified` outcome with exactly 1 flash attempt.
- **C7**: One-shot holdout failure — `handleVerificationPass` with a failing holdout verifier produces `qualification-failed` outcome with no repair events.
- **C8**: Repair success with rollback — flash fail → rollback → flash pass, asserting rollback event and terminal completion.
- **C9**: Pro escalation — two identical flash failures produce a `pro-escalate` decision with real routing decision IDs.
- **C10**: Rollback failure stops repair — failing rollback provider produces `stop`/`rollback-failed` with no subsequent routing decision.
- **C11**: Authority ambiguity — future-schema authority event causes `releaseToAuto` to throw.
- **C12**: Workspace-bound verification — workspace mutation changes the provenance hash.
- **C13**: Ledger secret sanitization — durable events contain no raw secrets after verification failure with secret-laden evidence.
- **C14**: Unpriced usage — `handleVerificationPass` throws `UNPRICED_USAGE` for an unknown model with no $0 fallback.
- **C15**: Trajectory reconstruction — `reconstructRepairState` recovers attempts, model, and routing ID from composed session history.

The Batch A runner (`scripts/run-v019-batch-a-evaluation.ts`) calls `runComposedRuntimeQualification()` after the verifier integrity check and exits with failure if the artifact is not ready. `generateRepoConfig()` is exported from `scripts/v019-trajectory-collector.ts` for qualification reuse.

The `ComposedQualificationRecord` artifact binds: `qualificationId`, `sourceCommit` (git HEAD), `timestamp`, per-check results, `passedCount`/`failedCount`/`skipCount`/`passed`, `backend` (enforcement and network denial), `filesystem` (read/write fences), `holdout` (model readability), `repair` (production runtime, rollback, provenance requirements), and `ready` (true only when all checks pass).

## Consequences

- Batch A cannot start paid execution until the composed runtime qualification is green, closing the gap between isolated mechanism tests and the real composed graph.
- The qualification reuses the exact Batch A config generator, so any future change to `generateRepoConfig()` that breaks composition fidelity will fail the gate before paid execution.
- The artifact records probed backend enforcement (from actual shell run `sandbox.enforcement`), not static platform preference — a Linux machine that falls back from bwrap to Landlock will report `partial` enforcement, not `full`.
- C3 uses `result.exitCode` and `result.sandbox?.denied` (not try/catch) to detect sandbox denial, because `shell.run()` resolves with a `ShellRunResult` on denial — exceptions are infrastructure failures only.
- C3 uses a harness-created secret file outside the workspace (not `/etc/passwd`, which bwrap/Landlock intentionally allow read-only) and `git ls-remote` (not `git fetch --dry-run`, which fails with "not a git repository" regardless of network state).
- C5 uses the actual sandboxed fs and bash for the agent side and host-side Node for the verifier side, establishing the asymmetric access property.
- C8 checks `passResult.verified` and state accounting (not `repair/completed` events) because `handleVerificationPass()` does not emit `repair/completed` — the plugin listener owns that event.
- C12 passes `changedFiles` to `handleVerificationPass()` and includes `tool/call` events so `changedFilesInTurn()` finds them, so the provenance provider hashes actual file content.
- The composed context is disposed (`ctx.fiber.dispose()`) and the fail-loud handler is uninstalled before the qualification returns, so the gate does not leak event handlers or plugins into the Batch A process.
- The qualification boots with a rollback provider (same as Batch A), so the "exact config" claim is true at the plugin level.
- Checks C6-C15 are labeled "helper-level" because they call exported repair-runtime helpers with synthetic sessions, not the full plugin→GoalService→completeVerified pipeline. A follow-up composed-evaluator scenario layer is planned to test the complete lifecycle through the running agent.
- Source fix: `handleVerificationPass()` now accepts `changedFiles` and passes them to the provenance provider, and provenance failure is fatal (fail-closed) rather than silently swallowed.
- Adding new security-critical capabilities to the Batch A composition requires extending the qualification with a corresponding check.

### Known limitations

- The freeze record and composed qualification artifact are now persisted to `artifacts/evals/`. On subsequent Batch A runs, the persisted freeze record is loaded and the current source is validated against its `verifierIntegrityHash`, and the persisted composed qualification artifact is loaded and matched against the current source commit. This binds the evaluation to a previously qualified source state rather than a hash generated and immediately verified in the same process run.
- Composed-runtime scenario checks (S1-S7) drive `verifyCompletion()` through the real GoalService and RepairRuntime plugin listener on the booted context's root agent, testing the full plugin→GoalService→completeVerified pipeline. S1 tests one-shot PASS→holdout PASS→goal complete. S2 tests diagnostic FAIL→repair evidence+decision. S3 tests post-verification `completeVerified` DENIED. S4 tests agent holdout access DENIED through the sandbox. S5 tests workspace-bound completion (no mutation → complete). S6 tests rollback failure stops repair with no new paid call. S7 tests authority ambiguity denies model transition.
- The freeze record now uses the probed backend from the composed runtime qualification rather than `platformEnforcement()`. The composed qualification boots the real Cordis context, runs shell commands through the actual sandbox, and records whether the backend denied network access. The freeze record's `backendEnforcement` field reflects the actual probed runner, not a static platform preference.
- Workspace-bound completion is now implemented in `completeVerified()`. The verification event carries an optional `workspaceHash` bound to the workspace state at verification time. At completion, the plugin re-computes the workspace hash and passes it to `completeVerified()`, which rejects mismatches with `GOAL_WORKSPACE_MUTATED`. The repair prompt now correctly states the workspace has been rolled back to the trusted base state.
- The verifier integrity file set now covers the composed qualification script, freeze generator, Batch A runner, repair-controller types, and goal domain — binding the full evaluator source closure to the freeze hash.
- Landlock does not isolate networking. A Linux runtime that falls back from bwrap to Landlock has filesystem isolation but not network isolation. The probed backend check reports this as `partial` enforcement, and the benchmark gate requires `full` enforcement (network-denied backend).
- The diagnostic verifier now captures real stdout/stderr from failed verification commands and passes them as evidence to the repair model. The repair model receives actual test failure output, assertion diffs, and build errors instead of a generic "diagnostic verification commands failed" message.
- Trajectory reconstruction groups `model/usage` events by `routingDecisionId` rather than counting one attempt per usage event. Provider retries within one logical attempt are aggregated — their tokens and costs are summed, and the attempt's latency spans from turn start to the last usage event. This prevents retry inflation of attempt counts, repair rates, and escalation rates.
- Control-plane and model-capability status now correctly distinguish infrastructure failures from model failures. `rollback-failed`, `workspace-provenance-failed`, and `unknown` outcomes produce `controlPlaneStatus=FAIL` and `modelCapabilityStatus=NOT_EVALUATED`, since the harness did not complete the evaluation pipeline and the model's capability cannot be assessed.
- Category metrics now apply the same `benchmarkEligible` filter as global metrics, preventing non-benchmark trajectories (e.g. B0 smoke tests) from contaminating per-category results.
- Failure taxonomy precedence corrected: F8 (repair evidence inadequate — same fingerprint repeated) is checked before F1/F17 (model reasoning / cross-file consistency), because a repeated fingerprint is more informative than "made changes but still fails." Deterministic fixtures in `v019-failure-taxonomy.spec.ts` validate each classification path and precedence ordering.
- The trajectory collector fails closed when paid requests lack canonical usage evidence: if `repair/evidence` events exist but no `model/usage` events are found, the collector throws `MISSING_USAGE_EVIDENCE` rather than silently producing zero-cost attempts.
- Verifier-controlled task files (package.json, tsconfig.json, vitest configs) are hashed before model execution. The diagnostic verifier re-hashes these files on each verification call and rejects the task if the model has tampered with them, preventing the model from altering test configuration or module resolution before final verification.
- Workspace verification hashing is unified: the same full-workspace SHA-256 algorithm is used at both verification and completion time. The provenance provider now computes `computeWorkspaceHash(workspace)` rather than hashing only changed files, which previously produced a different digest than the verification-time hash and caused `completeVerified()` to reject every legitimate completion.
- `verifyCompletion()` now accepts a `workspaceSnapshotProvider` function instead of a precomputed hash. The hash is computed AFTER all verifiers run, so it binds the workspace state that was actually tested. Diagnostic commands (test runners, type checkers) may create or mutate files during execution; a pre-verification hash would not reflect the verified state.
- `completeVerified()` now requires a current workspace hash whenever the verification event carries one. A missing current hash denies completion rather than silently bypassing the workspace binding.
- `GOAL_WORKSPACE_MUTATED` thrown by `completeVerified()` is now caught in the RepairRuntime plugin's pass handler and terminalized explicitly as a `workspace-provenance-failed` outcome with `repair/completed` and goal block, rather than escaping as an unhandled promise rejection.
- Rollback now preserves `node_modules`, `sessions`, `.git`, and `dist` directories by moving them to a temporary location before restoring source from the base commit, then moving them back. The previous implementation deleted the entire workspace and re-extracted from git archive, destroying installed dependencies and harness state, which could cause the second repair attempt to fail for infrastructure reasons misclassified as model failures.
- The Batch A trajectory collector now disposes its Cordis context fiber after every task via `ctx.fiber.dispose()` in a `finally` block, preventing event handlers, plugin effects, and session infrastructure from leaking into subsequent tasks in the same process.
- C5 and S4 (holdout secrecy checks) now call `fs.resolve()` before `fs.readText()`, matching the C2 pattern. The previous implementation passed a raw path string to `readText()`, which could throw simply because the argument shape was invalid, producing a false positive that the sandbox correctly denied holdout access.
- Composed backend qualification is now environment-bound. The qualification record includes `environment: { platform, arch, nodeVersion, runner }`. Persisted records are only reused when both the source commit and environment match. A source-match-only check could reuse a qualification generated on a machine with bwrap on a machine that falls back to Landlock, invalidating the backend qualification.
- C3 network tests now use a deterministic harness-owned local TCP listener on `127.0.0.1` instead of public-Internet DNS/HTTP/git tests. The sandboxed subprocess attempts to connect to the local listener; a network-isolating sandbox (bwrap `--unshare-net`, Seatbelt `deny network*`) denies the connection. This is deterministic and does not depend on external Internet availability, DNS, or proxy state.
- S2 now tests diagnostic PASS → holdout FAIL → qualification-failed by booting a fresh composed context with a failing holdout verifier, rather than testing diagnostic FAIL → repair evidence (which is a different scenario). The goal must be blocked with `qualification-failed` outcome and no repair evidence or decision events.
- S3 now genuinely mutates the workspace between verification and completion by writing to `src.ts` after verification, then calling `completeVerified()` with the current (mismatched) hash. The previous implementation tested idempotency (calling `completeVerified` twice), not post-verification mutation denial.
- S6 now boots a fresh composed context with a failing rollback provider to test rollback failure → terminal `rollback-failed` → no new paid call. The previous implementation used the main context's successful rollback provider and only checked that `repair/decision` fired.
- S8 (new) tests two Flash failures → real Pro routing → Pro PASS by booting a fresh composed context with a diagnostic verifier that fails twice then passes, verifying that `repair/decision` with `pro-escalate` action is emitted, `model/escalation` occurs, and the goal completes after the Pro attempt.
- Verifier-controlled file hashing now includes lockfiles (`package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`), test setup files (`tests/setup.ts`, etc.), and all test files in standard test directories (`tests/`, `test/`, `__tests__/`, `src/__tests__/`). The previous implementation hashed only `package.json`, `tsconfig.json`, and vitest/vite configs, allowing a model to tamper with test files or setup without detection.
- `buildFailurePackage` now includes `check.evidence` (captured stdout/stderr) in `failedCriteria` and `failingTests`, not just `typeErrors` and `buildErrors`. For diagnostic verifiers whose name does not contain 'test', 'type', or 'build' (e.g. `v019-diagnostic`), evidence content is classified by pattern matching (test runner output, TypeScript errors, build failures) so the repair model receives real diagnostic output regardless of verifier naming.
- Per-request usage reconciliation: each `repair/evidence` event is now checked for a corresponding `model/usage` event by `routingDecisionId` (or turn as fallback). A repair evidence event with no matching usage throws `MISSING_USAGE_EVIDENCE` with the specific routing decision and turn, rather than only checking the aggregate count.
- Trajectory joins now use `routingDecisionId` as the primary join key for model lookup and repair evidence/decision association, falling back to attempt ordinal only for legacy events that lack `routingDecisionId`. The previous implementation used turn-based matching as the primary join, which could mismatch when multiple routing decisions occurred on the same turn.
- `RepairCompletedEventData` now declares an optional `workspaceHash` field, making the workspace content hash bound to the terminal event part of the typed event schema.
- Failure taxonomy now has detection paths for F2 (repo-context: reference fix files not inspected, no changes), F3 (wrong-file: changes don't overlap reference fix), F7 (dependency: progress mentions module resolution errors), and F12 (timeout-latency: terminal outcome or abort reason indicates timeout). F4, F5, F15, and F16 are marked as manual-only via `MANUAL_ONLY_CATEGORIES` since they cannot be automatically detected from trajectory evidence.
- `CategoryMetric` now includes `eligibleCount` (benchmark-eligible tasks) alongside `count` (all tasks) and `evaluated` (eligible + evaluated). The previous implementation exposed only `count` (raw) and `evaluated`, making it ambiguous whether `count` included non-benchmark tasks.
- The composed qualification provenance provider now uses `computeWorkspaceHashForDir(workspace)` (full-workspace SHA-256), matching the live evaluator's `createProvenanceProvider` exactly. The previous composed-qualifier provider hashed only `context.changedFiles`, which could never match the full-workspace verification hash, causing S5 to fail for the wrong reason.
- Environment identity now detects the actual sandbox runner (`bwrap`, `landlock`, `seatbelt`, or `none`) by probing for platform-specific binaries, rather than hardcoding `sandbox-local`. `environmentMatches()` now compares `runner` in addition to `platform`, `arch`, and `nodeVersion`, preventing qualification reuse across different sandbox backends.
- `PRESERVE_DIRS` no longer includes `dist`. The `dist` directory is model/build-generated output, not harness state. Preserving it across rollback could contaminate the next attempt or final qualification. Only `node_modules`, `sessions`, and `.git` are preserved.
- The verifier-controlled file hash now includes `node_modules` integrity: the top-level package directory listing and lockfile metadata (`.package-lock.json`, `.modules.yaml`, `.pnpm/lock.yaml`). A model that modifies installed dependencies (e.g. patching vitest internals) will be detected. Full content hashing of `node_modules` is impractical; this detects structural tampering.
- S3 now mutates the workspace inside the snapshot provider (after computing the pre-mutation hash but before returning it), so the mutation occurs between verification and the first completion authorization — not after the goal is already terminal. The test asserts `outcome === 'workspace-provenance-failed'` and `goalPhase === 'blocked'`, proving the specific `GOAL_WORKSPACE_MUTATED` path was exercised, not just that `completeVerified` threw for any reason.
- Usage reconciliation now uses `model/routing-decision` events as the accounting population, not `repair/evidence`. Every routing decision represents a paid request and must have matching `model/usage`. This catches missing usage for one-shot success and final successful repair attempts, which have routing decisions but no repair evidence.

## Alternatives considered

- **Extending the existing security qualification with behavioral checks.** Rejected: the security qualification is source-composition focused and would grow beyond its scope. A separate composed-runtime gate keeps the two concerns distinct.
- **Running the full Batch A corpus as the qualification.** Rejected: paid execution cannot be the qualification gate — the gate must pass before paid execution begins.
- **Source-string checks only.** Rejected: source-string checks cannot detect dependency injection or registration defects, which is the motivating failure class.
